# DECISIONS.md

# MedGraph AI – Architecture Decision Record (ADR)

Version: 1.0 (Frozen)

---

# Purpose

This document records the major architectural decisions made during the design of MedGraph AI.

Each decision includes:

- Decision
- Rationale
- Alternatives Considered
- Reason for Rejection

This ensures the architecture remains consistent throughout development.

---

# ADR-001

## Decision

Use synthetic healthcare data generated by **Synthea**.

### Rationale

- Freely available.
- Realistic Electronic Health Record (EHR) structure.
- No privacy or legal concerns.
- Includes linked patient, encounter, medication, condition and observation data.
- Ideal for graph modelling.

### Alternatives

- MIMIC-IV
- Kaggle healthcare datasets
- Real hospital datasets

### Reason for Rejection

- MIMIC-IV requires credentialed access and is significantly more complex.
- Kaggle datasets are fragmented and often lack relationships.
- Real hospital data cannot be legally distributed.

---

# ADR-002

## Decision

Use **PySpark** for the ETL pipeline.

### Rationale

- Demonstrates scalable data engineering practices.
- Supports distributed processing.
- Produces reusable feature tables.
- Aligns with enterprise analytics workflows.

### Alternatives

- Pandas
- SQL scripts

### Reason for Rejection

Pandas is sufficient for small datasets but does not reflect the scalable ETL architecture this project is designed to demonstrate.

---

# ADR-003

## Decision

Use **Neo4j** as the operational database.

### Rationale

Healthcare records are highly interconnected.

Graph traversal is significantly more intuitive than complex relational joins for patient journey analysis.

Neo4j enables:

- Timeline reconstruction
- Relationship exploration
- Disease progression analysis
- Interactive graph visualisation

### Alternatives

- PostgreSQL
- MySQL

### Reason for Rejection

Relational databases store healthcare data effectively, but graph traversal requires increasingly complex joins as relationships grow.

---

# ADR-004

## Decision

Do not include PostgreSQL in Version 1.

### Rationale

The project does not require a relational operational database.

Neo4j stores healthcare entities.

Qdrant stores vector embeddings.

The ML model is persisted separately.

Adding PostgreSQL would increase operational complexity without providing a clear architectural benefit.

---

# ADR-005

## Decision

Use **Qdrant** as the vector database.

### Rationale

- Open source
- Docker friendly
- Local deployment
- Fast semantic search
- Simple integration
- Suitable for academic projects

### Alternatives

- Pinecone
- ChromaDB
- pgvector

### Reason for Rejection

Pinecone depends on an external cloud service.

ChromaDB is lightweight but less suitable for a production-style architecture.

pgvector would require introducing PostgreSQL solely for vector search.

# ADR-006

## Decision

Use **XGBoost** for prediction.

### Rationale

- Excellent performance on structured healthcare data.
- Fast inference.
- Mature ecosystem.
- Works well with SHAP.

### Alternatives

- Logistic Regression
- Random Forest
- Neural Networks

### Reason for Rejection

XGBoost provides the best balance between performance, explainability and implementation complexity.

---

# ADR-007

## Decision

Use **SHAP** for explainability.

### Rationale

Predictions without explanations are difficult to interpret.

SHAP identifies which features contributed most to a prediction, improving transparency and trust.

### Alternatives

- Feature importance
- LIME

### Reason for Rejection

Feature importance is global rather than patient-specific.

LIME is less consistent for tree-based models compared to SHAP.

---

# ADR-008

## Decision

Use **LangGraph** for workflow orchestration.

### Rationale

The platform coordinates multiple specialised components:

- Graph retrieval
- Risk prediction
- Guideline retrieval
- Report generation

LangGraph provides structured orchestration and conditional routing.

### Alternatives

- Sequential Python functions
- Simple prompt chaining

### Reason for Rejection

As the workflow grows, explicit orchestration becomes easier to maintain, extend and debug.

---

# ADR-009

## Decision

Use an **LLM only for report generation**.

### Rationale

The LLM receives:

- Graph results
- ML prediction
- SHAP explanation
- Guideline evidence

Its responsibility is to produce a coherent natural-language summary.

### Alternatives

Use the LLM for diagnosis or reasoning.

### Reason for Rejection

LLMs should not replace deterministic analytics.

The project prioritises explainability and evidence-grounded outputs.

---

# ADR-010

## Decision

Use **Qdrant-backed Retrieval-Augmented Generation (RAG)**.

### Rationale

Clinical explanations should reference trusted guideline documents rather than relying solely on model knowledge.

### Alternatives

- No RAG
- Internet search

### Reason for Rejection

Without retrieval, responses are more susceptible to hallucination.

Internet search introduces variability and dependency on external services.

---

# ADR-011

## Decision

The system is an **analytics platform**, not a clinical decision-support system.

### Rationale

The project focuses on:

- Healthcare analytics
- Knowledge graphs
- Risk stratification
- Explainable AI

It does not provide medical advice.

### Alternatives

Diagnosis assistant.

### Reason for Rejection

Clinical decision support introduces significantly higher validation, safety and regulatory requirements.

---

# ADR-012

## Decision

Adopt a modular architecture.

### Rationale

Each component has a single responsibility.

- PySpark → ETL
- Neo4j → Relationship storage
- Qdrant → Vector retrieval
- XGBoost → Prediction
- SHAP → Explainability
- LangGraph → Orchestration
- LLM → Report generation

This improves maintainability, testing and future extensibility.

---

# Final Principle

Every technology in MedGraph AI must solve a clearly defined engineering problem.

No technology is included solely to increase complexity or improve perceived resume value.

The architecture prioritises:

- Explainability
- Maintainability
- Scalability
- Modularity
- Reproducibility
- Evidence-grounded AI

These principles must remain unchanged throughout Version 1 development.
